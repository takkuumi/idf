# IMC v3.3.0 发布说明

日期：2026-11-15

## 封板状态

本版按生产封板基线验收。源码、三种硬件型号产物和真实设备验收结果必须保持
同一构建来源；交付包以干净 Git 提交重新生成，并以包内 SHA-256 清单作为唯一
交付依据。

## RS485-1 修复

F3 RS485-1 在部分外部收发器/转换器组合下会把本机发出的 Modbus 应答回送到 UART RX。此前从站把一次 UART 批次当作单帧处理，出现“应答回显 + 下一条请求”时整批 CRC 失败，导致 2300 起 100 个寄存器读取交替超时。

3.3.0 增加有界 RTU 请求帧提取：只调度站号、功能码、请求长度和 CRC 均正确的请求；忽略本机响应和异常响应回流，不再因回显触发二次应答。GPIO19 继续只作为 `485_AD0` 地址拨码输入，不作为 DE/RE。

## 验证

- 主机生产回归：28/28 通过。
- F3/F4 `cargo check --locked --bin imc` 通过。
- F3 真实链路：FC03 地址 2300 数量 100，正常完整帧 205 字节，CRC 和数据均与 TCP 一致；当前源码重建后连续 1000/1000 成功，完整响应平均 232.310ms，最大 252.877ms。
- 修复前极限压测：100 次中 50 次成功、50 次超时；UART1 收到 102 帧、只应答 51 帧，失败批次出现 213 字节，确认回显/粘帧根因。
- 真实测试原始记录：`log/hardware/rs485-f3-2026-11-14/rs485-1-poll-2300x100-soak-20261114-230700/`、`rs485-1-tail-capture-234755/`。

## OTA 兼容性（2.9.0 → 3.3.0）

同一硬件型号可以从 v2.9.0 通过 Web OTA 升级到 v3.3.0。两版的分区表字节级
一致，`factory`、`ota_0`、`ota_1` 均为 `0x240000`，NVS schema 均为
`0x0207`，holding 双槽 magic/version 也保持一致。v3.3.0 F3 App 为
`1,854,432` 字节，低于 `0x240000` OTA 槽容量。

现场操作要求：

1. F3 只能上传 `imc-v3.3.0-f3-app.bin`；DEFAULT 和 F4 必须使用对应目录的
   App，禁止跨型号上传。
2. Web OTA 只上传 `*-app.bin`。`*-ota-data-initial.bin` 是新设备完整烧录用的
   OTA 选择数据，不能作为 Web OTA 固件上传。
3. OTA 升级不会擦除 NVS、holding、组态、网络和端口配置；升级过程中不要断电，
   等待设备自动重启并完成约 30 秒稳定确认窗口。
4. v2.9.0 设备若仍是旧的单 factory 分区表，不能直接 OTA；必须先按完整刷机
   流程迁移到本项目的双 OTA 分区布局。标准 v2.9.0 生产包已经是当前布局。

详细证据、版本矩阵和现场检查表见
[v2.9.0→v3.3.0 OTA 兼容性记录](../testing/ota-v2.9.0-to-v3.3.0-2026-11-15.md)。

本版本不修改 GPIO 地址拨码定义。RS485-1 当前源码重建后的 1000 次极限压测
已完成，详细数据见验收记录和逐次日志。

## 三种型号封板产物

| 型号 | App 大小 | OTA 槽占用 |
|---|---:|---:|
| DEFAULT | 1,861,040 B | 78.9% |
| F3 | 1,854,432 B | 78.6% |
| F4 | 1,854,608 B | 78.6% |

三种 App 均小于 `0x240000` OTA 槽；每个目录同时提供 bootloader、分区表、
初始 OTA data、factory 镜像、manifest 和 SHA-256 清单。

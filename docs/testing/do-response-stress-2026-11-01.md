# DO 写入与读回连续压测（2026-11-01）

## 台架与测量边界

- 用户明确确认空载测试板、全部 Q 点可切换；F3/PCA9555，16 路 DO，固件 2.4.0，IP `192.168.51.227`。对照 build `928fe474ff29`，修复后 build `a988c46ae8f7`。
- 保持当前参数与组态，不改模式、引脚、版本或 Flash 布局。首轮输出原值 `0xD011`；后续观察到其它控制源写入，用户确认暂停其它操作后，独占窗口重新备份当前值 `0xFE07`，结束时恢复本次基线，不覆盖回更旧的值。
- 写应答只说明命令已受理。FC01 读的是软件目标；最终确认来自 worker 实际 I2C OUTPUT 寄存器读回，必须校验有效性、位图、确认代号与队列清空。
- 没有示波器/触点回接，不能把寄存器读回说成继电器触点或负载动作时间。报告的寄存器观察延迟包含主机、网络、HTTP 轮询开销，是本次观测的端到端时延。

## 方法

- 工具：`tests/manual/do_response_stress.py`，显式 `--apply`，备份路径必须不存在。
- 计划 600 秒连续切换，先 60 秒空闲，后 540 秒叠加 502/503/504/5002 四连接持续读负载；每次切换确认完成后再发下一条，命令发起间隔至少 100ms，实际频率由读回耗时决定。
- 轮换 Web `/iocontrol`、Modbus FC05 单点、FC15 全位图写入；包括逐点翻转、全开、全关、交错位、逐位开/关。
- 每笔验证写应答、FC01 整个位图与硬件寄存器位图；记录确认代号、轮询次数、读回龄期、写应答/线圈读/寄存器观察延迟。任一超时或不一致终止测试并尝试恢复。
- 30 秒健康采样，检查复位计数；连续收集 UART，并核查 DI/DO/LED 事务、队列拒绝和故障取消计数。恢复后留出既有持久化任务观察时间并再次读回，不把等待等同于已经断电验证。

## 启动探测记录

- 首次普通串口 monitor 打开后网络与 UART 无响应，尚未进行本轮 DO 切换；释放串口控制线后观察到 POWERON 启动，计数从 141 到 142。随后重新连接采集器再次观察到启动，计数到 143。
- 该现象与台架串口控制线/驱动打开操作相邻，属于测试前必须保留的观测；没有 EN/GPIO0 电气波形，不能仅凭此证明具体哪条控制线产生脉冲。未观察到这两次启动前的软件 panic 或看门狗证据。
- 串口采集改为打开前设置非活动 DTR/RTS；不宣称能消除驱动打开时所有瞬态。先固定 UART 连接并等待网络就绪，再开始正式连续窗口；本次窗口基线 reset_count=143。
- 两次连接失败原始日志保留，未覆盖成通过记录。重新启动日志确认仍为同一 build，DO 从 NVS 恢复 `0xD011`。

### 认证及并发操作中止

- 修复版第一次尝试在 30.31 秒、289 笔成功确认后遇到认证 API 非 JSON 响应，脚本中止；该次未保存最终 URL/MIME，不能仅凭工具的 `Web session changed` 文本证明具体是谁登录或响应来自哪条路径。
- 该次 cleanup 已经经 FC15 下发原值，但随后硬件确认受认证接口阻断，工具按 `restored=false` 报告，不把命令应答当成恢复成功。后来独立读取观察到 `0xFE07`、确认代号 307；高于该次脚本的最后代号与一次恢复提交，表明仍存在额外输出写入。参数读回无变化、reset_count 保持 144，未见 panic/I2C 事务错误。
- 用户随后明确确认暂停手持机/Web 操作，允许 10 分钟独占写入及登录。新窗口从当前 `0xFE07` 另建备份，失败尝试日志完整保留，不合并为通过成绩。
- 工具改为在非 JSON 时记录状态码、最终 URL 与 Content-Type；普通测量仍严格失败终止，仅恢复核验阶段允许重新登录一次，且保留原测试错误。

## 首轮发现及修复

- 旧候选 `928fe474ff29` 的首轮于 137.37 秒主动中止，完成 1,067 笔写入/线圈及寄存器核对，无不一致，原输出已恢复；这不是已完成的 600 秒测试。
- 连续写入与 Web 诊断并发时出现 `DO queue busy`：主循环把非阻塞队列锁争用当成 I2C 故障，退避 100ms；不是输出寄存器 NACK，但会人为扩大尾延迟。
- 将暂未受理的队列争用/满队列返回类型化 Busy，保持 dirty 与旧 last，下一主循环 tick 再提交；真实 I2C/驱动故障仍保留原 100ms 退避。Poisoned 与暂时争用分开处理，不因降级分类而隐藏损坏。
- Web 诊断只在队列锁内复制固定字段，释放后再格式化 JSON；新增 `do_submit_busy` 计数，不再用硬件故障日志表达正常软件背压。
- 新增实际提交路径的锁争用、满队列拒绝、恢复与 poisoned 测试；主循环提交结果测试验证忙时不推进 last、不增加硬件失败计数且不进入 100ms 等待，真实故障仍等待完整间隔。
- 主机核心 27 项通过，实际 F3/F4 提交与事务各 8 项通过（包括共用队列用例）；三种硬件特性 Clippy 零 warning，F3 设备测试目标仅编译通过。最终 F3 release 构建通过，并独立核对 bootloader、分区表、擦除后的 otadata 和应用四段 Flash digest 全部匹配。
- 修复镜像应用 1,773,280 bytes，2,359,296-byte OTA 槽余量 586,016 bytes（占用 75.16%），候选目录 `release/candidates/v2.4.0-do-response-20261101-a988c46`，保持此前正式发布包不变。

## 最终复测结果

- 本地时间 2026-11-01 08:15:10 至 08:25:12（UTC 00:15:10 至 00:25:12）。有效连续观察 600.025s，加恢复核验全程 602.551s；完整完成，未中断。
- 4,160 笔实际 DO 写入均经过写应答、FC01 全位图及 OUTPUT 寄存器确认，零超时、零不一致；空闲 578 笔，加载四端口后 3,582 笔。16 路均覆盖上升和下降，确认代号 307 → 4,467，每笔恰好推进一次，无跳号。
- 502/503/504/5002 并发后台读取合计 92,878 请求，零错误；本窗口无认证替换。45 次短暂提交争用正常重试，队列高水位 1、拒绝和故障取消均为 0，未再出现旧版的 queue-busy 硬件故障告警。
- 复位计数保持 144；健康采样恢复模式 Normal、故障计数为 0、DI/DO 读回有效，DI/DO/LED 事务错误均为 0。串口无 panic、WDT、栈溢出或新的 ERROR；启动时 RS485-3/校准提示和独占窗口前的 BLE 断开记录单独保留。
- 当前四类网络/串口/BLE/校准 API 参数与本次基线一致。原输出 `0xFE07` 已恢复，留出后台持久化观察时间后再次确认，结束串口监控后又经 FC01 独立复读一致；没有覆盖回旧的 `0xD011`。本次没有执行额外断电来证明恢复值落盘。
- 最小采样 free heap 2,084,880B；本镜像内部 SRAM 水位约 41KiB。注册任务 8 个、low=0，最小剩余栈 1,852B（mb-rtu-port1，最高使用 77%）。不同测试路径水位不可直接作为相对旧候选的栈优化结论。

### 性能结论与边界

- 确认去除了“暂时争用 → 人为等待 100ms”的错误路径，真实故障退避和固定容量背压保留；本轮实际触发的 45 次争用全部正确恢复。
- 整体观测尾延迟仍受网络、HTTP、Flash 与调度影响，最大观察到 363.44ms；新旧窗口时长与样本量不同，不能用单次 max 或少量分位数差异宣称整体获得倍数提升。
- 饱和负载主循环工作 P95/P99 桶上界为 7.5ms，本镜像串口最大工作时间 66.738ms，并存在 deadline miss；5ms 是目标调度周期，不是已证明的硬实时期限。
- 没有触点回接/示波器、带负载电气测试、物理 I2C 拔板、F4 真机或本镜像 8h/72h 长测；本次通过范围是这块空载 F3 上的持续写入、目标读取与真实输出寄存器确认。

# DO 写入与读回连续压测（2026-11-01）

## 台架与测量边界

- 用户明确确认空载测试板、全部 Q 点可切换；F3/PCA9555，16 路 DO，固件 2.4.0，build `928fe474ff29`，IP `192.168.51.227`。
- 保持当前参数与组态，不改模式、引脚、版本或 Flash 布局。输出原值 `0xD011`，测试前保留独立备份，结束时恢复该值。
- 写应答只说明命令已受理。FC01 读的是软件目标；最终确认来自 worker 实际 I2C OUTPUT 寄存器读回，必须校验有效性、位图、确认代号与队列清空。
- 没有示波器/触点回接，不能把寄存器读回说成继电器触点或负载动作时间。报告的寄存器观察延迟包含主机、网络、HTTP 轮询开销，是本次观测的端到端时延。

## 方法

- 工具：`tests/manual/do_response_stress.py`，显式 `--apply`，备份路径必须不存在。
- 计划 600 秒连续切换，先 60 秒空闲，后 540 秒叠加 502/503/504/5002 四连接持续读负载；每次切换确认完成后再发下一条，命令发起间隔至少 100ms，实际频率由读回耗时决定。
- 轮换 Web `/iocontrol`、Modbus FC05 单点、FC15 全位图写入；包括逐点翻转、全开、全关、交错位、逐位开/关。
- 每笔验证写应答、FC01 整个位图与硬件寄存器位图；记录确认代号、轮询次数、读回龄期、写应答/线圈读/寄存器观察延迟。任一超时或不一致终止测试并尝试恢复。
- 30 秒健康采样，检查复位计数；连续收集 UART，并核查 DI/DO/LED 事务、队列拒绝和故障取消计数。恢复后留出既有持久化任务观察时间并再次读回，不把等待等同于已经断电验证。

## 启动探测记录

- 首次普通串口 monitor 打开后网络与 UART 无响应，尚未进行本轮 DO 切换；释放串口控制线后观察到 POWERON 启动，计数从 141 到 142。随后重新连接采集器再次观察到启动，计数到 143。
- 该现象与台架串口控制线/驱动打开操作相邻，属于测试前必须保留的观测；没有 EN/GPIO0 电气波形，不能仅凭此证明具体哪条控制线产生脉冲。未观察到这两次启动前的软件 panic 或看门狗证据。
- 串口采集改为打开前设置非活动 DTR/RTS；不宣称能消除驱动打开时所有瞬态。先固定 UART 连接并等待网络就绪，再开始正式连续窗口；本次窗口基线 reset_count=143。
- 两次连接失败原始日志保留，未覆盖成通过记录。重新启动日志确认仍为同一 build，DO 从 NVS 恢复 `0xD011`。

## 首轮发现及修复

- 旧候选 `928fe474ff29` 的首轮于 137.37 秒主动中止，完成 1,067 笔写入/线圈及寄存器核对，无不一致，原输出已恢复；这不是已完成的 600 秒测试。
- 连续写入与 Web 诊断并发时出现 `DO queue busy`：主循环把非阻塞队列锁争用当成 I2C 故障，退避 100ms；不是输出寄存器 NACK，但会人为扩大尾延迟。
- 将暂未受理的队列争用/满队列返回类型化 Busy，保持 dirty 与旧 last，下一主循环 tick 再提交；真实 I2C/驱动故障仍保留原 100ms 退避。Poisoned 与暂时争用分开处理，不因降级分类而隐藏损坏。
- Web 诊断只在队列锁内复制固定字段，释放后再格式化 JSON；新增 `do_submit_busy` 计数，不再用硬件故障日志表达正常软件背压。
- 新增实际提交路径的锁争用、满队列拒绝、恢复与 poisoned 测试；主循环提交结果测试验证忙时不推进 last、不增加硬件失败计数且不进入 100ms 等待，真实故障仍等待完整间隔。

# 3.2.0 RTU / LoRa 时延根因与验收门槛

## 实测根因

在正常 LoRa 透传路径上，通过 Web OTA 安装只读计时镜像（UART/GPIO/超时策略保持原样），分段记录：

- 9600bps 8-byte 请求收帧等待：4009711µs / 4009981µs。
- 9-byte 应答组包323µs，UART发送9683µs，总服务10094µs。
- 245-byte 应答组包381µs，UART发送256126µs，总服务256616µs；15秒完整捕获获得全部245bytes并与TCP逐字节一致。

`rtu_silence_us(9600)` 约4010微秒，而初版 `rtu_silence_timeout_ms` 未除1000，直接当成约4010毫秒传入阻塞读取。一次阻塞读取还可能越过整个250ms帧deadline。它在共享 RS485 端口实现中，同时影响物理 RS485 和 UART0 LoRa。

不能再归因于无线模块参数，也没有证据支持先前的 SDK 发送环形缓冲越界猜测：SDK 内部已按最大单块限幅。早先5秒测试的迟到应答、后续请求及部分帧不能当作独立RF丢包证明。

## 修复

- 生产时序逻辑抽为 `src/rs485/timing.rs`，微秒先除以每tick微秒数，再得到tick对齐毫秒。
- 9600bps / 1ms tick 的 t3.5 为5ms；>19200bps采用 Modbus 串行规范建议固定1750µs，向上取整到2ms。
- 每次字节读取以剩余完整帧预算为上限，允许至多调度tick取整，不能一次额外阻塞数秒。
- 首字节快速失败策略保持；收到数据之后按实际波特率/字符位数为合法长帧分配预算。1200bps最大8E2帧超过2秒，实际线长预算可至3秒，不扩大离线首字节等待。
- 每端口无分配计数和分段耗时通过只读 Web diagnostics 发布；HTTP端有限次一致快照重试，不阻塞 UART。增加运行构建ID、OTA分区及确认状态，便于核对真实运行镜像。

## 测试

- `tests/host/run_uart_timing.py` 直接提取生产包装函数，并加载实际纯时序模块。修复前9600→5ms回归测试实际失败；修复后8项通过。
- 波特率1200..921600、1/2/10ms tick、完整帧预算、剩余预算、非法值溢出边界覆盖。新增UART trace 3项含20000次并发一致快照。

- 实机修复后还须逐档LoRa长短帧、DO/配置/连接/OTA等完整回归。最终结果追加在本报告和 `log/hardware/v3.2.0-full-acceptance-2026-11-14/`。

## FIFO 分段的第二项实机缺陷

049621a 修正单位后，LoRa 小帧约0.5秒；FC16 1/16个寄存器写入并回读、恢复通过，但60个寄存器的129-byte请求失败。UART trace 中总RX比已处理TX多2次、最后一次RX仅9bytes，符合120+9分段。默认FIFO 120-byte门限在9600bps连续输入时可隐藏约125ms，上层6ms空闲不能据此认定线缆真的空闲。

后续调整采用随波特率和实际字符位数变化的FIFO投递门限，使批次时长不超过半t3.5且最多约1ms；高速批量投递避免每字节一次中断。接收等待多留一个FreeRTOS tick相位余量，但仍受剩余总预算约束。TX ring从256分离为512bytes，使一个最大RTU帧及驱动元数据可完整排入，三路共增加768bytes，不增任务栈。该项须在下一镜像真实长帧读写和系统并发中验证。

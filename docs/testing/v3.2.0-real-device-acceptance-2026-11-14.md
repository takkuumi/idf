# IMC 3.2.0：Web、AI 与真实设备回归

日期：2026-11-14，Asia/Shanghai。F3 / ESP32-S3 rev v0.2 / 8MB；设备 MCU MAC `FC:01:2C:05:64:88`，以太网 MAC `FC:01:2C:05:64:8B`，IP `192.168.51.226`。

原始记录：`log/hardware/v3.2.0-acceptance-2026-11-14/`。这是当日有限时长的台架验收，不是 7×24 或可用性“几个 9”的统计证明。

## 1. AI 原因、修复与证据

链路为 ADC DMA → 100ms tick → 8 点滑动平均 → 校准端点 → 反向 0..4095 归一化 → input registers / Web。同一板、用户确认无电流设备连接时，先刷只增加只读原始 ADC 诊断的镜像，**不改变换算函数**取得 60 组样本：

| 通道（Web 编号） | 原始 ADC 最小～最大 | 旧归一化值 | 已存 MIN/MAX |
|---|---:|---:|---:|
| AI0 | 2945～2948 | 116～121 | 0 / 2941 |
| AI1 | 2943～2947 | 118～124 | 0 / 2942 |
| AI2 | 2943～2947 | 118～124 | 0 / 2942 |
| AI3 | 2944～2948 | 116～123 | 0 / 2942 |

旧代码在 MIN 或 MAX 任一为 0 时，将整对端点替换为 605/3016。以 raw=2944 为例，`4095 + trunc((2944-605)*-4095/2411) = 123`。**240/240 个值与此旧路径逐项精确吻合**，证明空载偏值来自已存零点未应用，不是 Web 把数值改乱。参考旧固件也有整对回退行为，不能作为正确性的依据。

修复：仅为缺失的一端补默认参考；有效已存端点保持；反向、相等、超过 4095 的端点组合安全回退。后续当前版本进一步把“两端均为 0/非法”标为未标定，工程量不再使用默认参考冒充有效输入；原始 ADC 仍由 Web `ai_raw` 提供诊断。没有扩大原 `<20` 清零死区，没有用当前未知输入自动归零，没有改写现场标定。

另修复平均窗口启动除数：当前样本已进入 sum，却仍除以之前的 filled，第二次会以一个样本作除数。新实现先将样本数加一再求平均，满窗口行为保持。生产函数抽为无分配模块 `src/channel/ai_transfer.rs`，10 个可执行 host 测试覆盖 4/8 通道、启动、满窗、阶跃、单端/双端/缺失/错误标定及全 4096 个 ADC 码的单调和饱和边界。原有一条仅编译未执行的测试把整数截断结果 21 错写为 20，已修正测试期望，保留既有 IMC 整数映射函数。

修复候选 3.2.0 连续 **120 组 / 480 个数值**：四路归一化值全部为 0，原始 ADC 范围合计 2943～2949；按生效端点复算无偏差超限。`ai_effective.source=zero` 如实表示仅保存零点、满量程端仍为默认参考。

**精度边界**：这是已存端点应用、数学归一化和空载零点验收。数值单位是 ADC 归一化码，不是 mA。没有标准电流源，不能宣称已验证 4/12/20mA 精度、各通道增益或全量程线性。没有有效端点的新板仍须进行规定的现场/出厂标定，不能将默认参考等同于实测标定。

证据：`diagnostic-ai/`、`fixed-ai/`、`tests/manual/ai_idle_acceptance.py`。

## 2. Web 会话与布局

浏览器直接加载仓库内嵌页面，通过本地 HTTP 测试服务验证异常路径，并在真实设备上用第二次登录替换第一会话：

- 页面全部 **14 个不同 API 路径**的登录重定向均自动进入 `/login`；HTTP 401、403 同样处理。退出时只发起一次页面替换并停止后台轮询。
- HTTP 500 和网络错误不误判为登录失效。
- OTA XHR 登录失效也自动跳转。测试固件字节只发给本地测试 HTTP 服务，未向设备 OTA 上传无效镜像。
- 真实设备被新会话替换后，原浏览器自动退出通过。24 小时 TTL 未以实际等待 24 小时替代测试，覆盖的是同一认证失效响应分支。
- 每路 RS485 采用独立卡片，18px 内边距、16px 卡间距与字段间距；I 点有效状态使用 **18px 绿色实心圆点**，其余状态指示点 14px。
- 1440px 桌面与 390px 窄屏、2 倍像素密度检查：无横向溢出，三张端口卡片尺寸和间距断言通过，并留截图人工查看。
- 登录密码默认隐藏；可见开关在空值、含中文/符号测试值、连续切换时保留输入、正确更新可访问状态且不提交表单。

证据：`web-browser/`、`web-browser-final-layout-local/`；正式镜像刷后复核另记 `final-web-browser/`。页面仍是原生 HTML/CSS/JavaScript，没有新增前端运行依赖。

## 3. 通信、资源与持久化

将前轮 3.1.0 实机发现的组态末块栈溢出、BLE 请求发布丢失修复一并纳入 3.2.0；不能用旧 3.1.0 初版归档交付。

- BLE 纯读取压力 180 秒，整轮 **2888 次成功请求**，0 请求超时、0 CRC/帧错误，5 次重连成功；均值 64.65ms、P95 90.16ms、P99 119.35ms，包含主机与 BLE 往返。
- 第二轮含 30 秒读取、持久化与组态，**810 次成功请求**，0 超时/帧错误。15 条主动通知明确解析为心跳，非丢失的请求应答。

- 连接回收：7 个未发请求的连接按时回收，既有有效连接保持、新连接可用；随后 100 次跨四端口建连读取 0 失败。
- BLE 位置标记写入后立即软复位，回读标记正确，再恢复原值并复位；1700-word 组态和 2000-word 文本保持。

- 原 IP/掩码/网关/DNS、串口、BLE、标定、组态和文本均已恢复；未主动翻转 Q 点，Q6/Q7 输出寄存器回读仍为 `0x0060`。输出寄存器回读不等于继电器触点的独立测量。

## 5. LoRa 测试条件纠正

用户明确确认：板上 LoRa 是 UART0 透明透传；下载通路占用时 LoRa 不可用。此前外置对端在 `/dev/cu.usbserial-14120`、重枚举后的 `14110/14140` 上无响应、不同波特率探测、2.9.0 与 11 月 12 日原始 2.7.0 镜像对照，都在板上下载 USB 仍连接的条件下进行。**这些轮次的 RF 测试前提不成立，不能用于证明 LoRa 故障或固件回归，也不应记成正常工作模式下的 LoRa 验收失败。**

原始日志保留，分类纠正见 `lora-test-condition-correction.json`。原始成功镜像 SHA `377caa8e587c6289449321ad47ef3fd83a32f4d6c58ea22870e8720ed90cf6be` 在 A/B 对照后已退出，设备恢复正式 3.2.0。临时只读 UART 查询仅确认驱动和波特率，不能证明硬件通路已接到 LoRa；相关临时查询已从正式源码移除。

有效 RF 验收的前提是：设备独立供电、板上下载 USB 拔掉、电脑保留外置 E22 对端。先观察下载口消失及网络仍在线，再从外置对端发送真实 FC01/02/03/04 只读请求，与同设备 TCP 返回的版本、MAC、组态及长文本核对。结果单独保存在 `final-lora-working-mode*`，未满足这个前提时不发送验收请求。

`F3-GPIO.xlsx` 只直接证明 GPIO43/44 被标为 USB 烧录口/LoRa 共用，未附 BCT4227 原图或 VBUS→选择脚网络；具体选择极性仍须原理图或实际拔线对照。不能绝对相信先前文档把 VBUS 写成已确认根因的描述。

本轮没有独立的物理 RS485 主站/从站完整闭环、NFC 手机 RF/掉场、AI 标准电流源及继电器带载条件；这些项目必须单独验收，不能据本报告声称所有外设 100% 正常。

### 正常 LoRa 通路与软件强制模式实测

下载口于 12:16:52 消失、以太网仍可访问后，才开始有效 RF 测试。正式 3.2.0 的版本、MAC、AI、FC01/02 位状态与 60-word 组态读取能双向通信并匹配 TCP。此前“完全不通”属于下载通路占用，不能列为固件回归。

有效混合轮次 14 请求中 12 成功；120-register 文本长读两次未通过（一次仅收到与期望帧末尾一致的 5 字节，另一次超时）。成功请求平均完整 RTT 4655ms、最大 5294ms，明显不同于 11 月 12 日短读约 235ms 的条件。调整外置适配器 DTR/RTS 的 True/True 与 False/False，6 次标准短读均通过，但 RTT 仍约 4511～4516ms，不能据此归因于控制线。单独不解析帧的 20 秒长读也未取得完整 245-byte 响应。当前仅确认基本透传恢复，**长帧可靠性与高时延未完成归因，不属于全功能 RF 通过**，没有盲改无线参数或全局 RS485 收帧逻辑。

用户提出保持下载 USB 插着、通过软件强制正常模式；已新增 `tests/manual/uart0_route_acceptance.py`，在板上下载口重新接入后执行：

| DTR / RTS | TCP 应用运行、版本 3.2.0 | 10 秒 RF 应答 |
|---|---|---|
| False / False（释放） | 正常 | 无 |
| True / True | 正常 | 无 |
| True / False | 正常 | 无 |

先释放 BOOT 并脉冲 EN 强制正常启动，结束再释放控制线并复位，均验证应用正常。该实测说明：在当前板及接法下，软件把 MCU 退出 ROM 下载器，并不足以恢复插线状态的 LoRa 通路。不能把 ROM 下载/运行状态与外部 UART0 选择通路视作同一状态。若要实现插线时强制切回 LoRa，需要原始原理图确认选择脚的真实控制来源；当前 GPIO 表无法提供这一证据，不能猜测驱动 GPIO26 等引脚。

证据：`final-lora-working-mode-watch.jsonl`、`final-lora-mixed-long-timeout/`、`lora-working-modem-lines.jsonl`、`lora-large-frame-raw-capture.json`、`forced-normal-route/`。

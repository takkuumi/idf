# v3.3.0 F3 TCP + RS485 + BLE 全链路压力验收

日期：2026-11-15（Asia/Shanghai）  
固件：v3.3.0，build `5161ae8c8983`，F3，factory 分区  
设备：`192.168.51.226`，MAC `fc:01:2c:05:64:8b`  
测试方式：只读 Modbus FC03，未写 Q 点、配置或持久化区，未复位设备。

## 结论

- TCP、RS485-2、BLE 三链路同时运行 10 分钟时，合计 87,323 次读事务全部成功；设备未复位，链路错误计数、DI/DO 故障计数均未增加。
- 三链路同时运行且保持 7 个 TCP 客户端时，120 秒内 TCP/RS485/BLE 共 16,431 次读事务全部成功。6 客户端对照 120 秒也全部成功。
- **8 个 TCP 客户端未通过**：无论三链路并发还是仅 TCP，第二个连接到 503 端口的测试客户端都被设备端复位/关闭，导致它持续重连。三链路 8 客户端阶段 TCP 错误 2,851 次；TCP 单链路 8 客户端对照错误 459 次。RS485 与 BLE 在对应阶段没有请求错误。
- 压测暴露并确认了连接边界：旧固件 `MAX_CONNECTIONS=8` 时已有 1 个常驻 Modbus TCP 会话，8 个业务客户端因此有 1 个被拒绝。已将槽位扩为 9，并增加 Web 诊断字段；修复后的 8 客户端 TCP-only 和三链路压力均通过。旧版失败数据仍保留为根因证据，见本报告“修复后复测”。
- 本轮数据支持“当前设备在本测试负载下三链路协调运行稳定”，不构成所有现场网络、PLC 主站数量、RS485 总线负载及 7×24 全场景的数学保证。

## 环境与方法

- 主机：macOS 26.7.2 x86_64，Python 3.9.6；主机经 Wi-Fi、路由器访问设备 W5500 以太网，TCP 往返时间包含该网络路径。
- Modbus TCP 端口：502、503、504、5002。四端口轮转；使用持久 TCP 连接，最多启动 8 个客户端。
- RS485：`/dev/cu.usbserial-14140`，9600 8N1，站号 1，FC03 地址 2300。物理端口按设备诊断 UART2 收发计数确认。只读帧，逐帧校验长度、CRC 和数据与 TCP 基准一致。
- BLE：macOS CoreBluetooth 原生 GATT，按 IMC Service 读取地址 2300 的同一静态寄存器数据；核验 BLE 返回内容。计划重连阶段每 25 秒主动断开重连。
- 请求数量循环：1、2、8、32、100、125 个寄存器；bulk 阶段循环 100、125 个寄存器。每条链路无额外应用层节流，设备健康接口约每秒采样一次。
- 分位数按成功请求的完整往返毫秒计算；吞吐按成功事务数除以实际观测秒数。请求/应答数据校验失败均计错误，不以重试后的成功覆盖原始失败。
- 完整原始 JSONL、目标固件身份、配置前后哈希与健康快照保存在 `log/hardware/full-link-2026-11-15-v330/` 和 `log/hardware/full-link-2026-11-15-capacity-compare/`。

主压力运行共 184,002 次成功事务。8 客户端阶段的 2,851 次 TCP 错误来自一个客户端反复连接后，在收到 Modbus 响应前被对端 reset/close；错误都在 `joint_8_clients` 与 `joint_8_bulk`，不影响其余 7 条 TCP 流以及同时运行的 RS485/BLE。`*` 三次 BLE 错误发生在脚本设定的周期断连窗口，均为断开先于当前响应；不属于 BLE 在稳定连接阶段的丢包，但仍按请求错误保留。

吞吐中的有效字节只计寄存器数据（每寄存器 2 字节），不含 Modbus、TCP/IP、BLE、RTU 帧头及链路重传。600 秒稳定混合负载阶段，三链路合计 **145.52 req/s、13,000.2 有效 B/s（约 12.70 KiB/s）**，是本轮无错误持续阶段的代表值。bulk 场景下各链路最高测得：TCP **25,911 B/s**、RS485 **830 B/s**、BLE **3,341 B/s**；bulk 阶段 8 TCP 客户端有失败，因此这些峰值表示已校验成功请求的负载速率，不表示 8 客户端场景全链路通过。每阶段各链路有效吞吐均记录在对应 `analysis.json` 的 `useful_bytes_s`。

## 设备健康与数据完整性

- 主压力期间健康采样 1,457 次；设备 uptime 从 18,284 秒递增到 19,751 秒，`reset_count` 全程保持 155；无复位、链路掉线或 uptime 回退。
- 宏观空闲堆采样范围 2,077,316–2,085,764 字节；结束后 2,084,880 字节。压测结束后堆恢复至采样范围高位附近，没有观察到持续性堆下降。
- recovery mode 全程 `Normal`；`degradable=0`、`severe=0`；三路 RS485 `comerr/apperr` 都保持 0；BLE drop 计数始终为 0（脚本计划断开不计为链路 drop）。
- Web IO 诊断采样中 DI/DO failures=0、输出队列拒绝=0、队列高水位=1。main-loop 最近 60 秒窗口最大工作时间最高 27.478 ms，窗口 P95/P99 上界最大均为 20 ms；IO loop 报告最大值 84.994 ms。此项是诊断窗口统计，不等同于外部实时调度器的硬实时上界。
- 测试前后 holding 组态、长文本与 RS485 端口配置的 SHA-256 完全一致；固件 build ID、factory 分区均未变化。
- 容量对照另采样 308 次；reset_count 仍为 155，最小 free heap 2,076,168 字节，RS485/IO/系统故障计数均无增长。

## 通过范围与遗留项

- 在当前 F3 样机、静态 FC03 数据、指定 9600 8N1 RS485-2 对端和网络路径下，4/6/7 TCP 客户端三链路并发的请求与数据校验通过；10 分钟连续混合负载期间设备健康指标稳定。
- 旧构建的失败与修复构建的通过都在本报告保存，避免把前者误读成当前固件仍失败，或把配置变更未经实测就当作通过。
- 新增字段 `tcp_active_connections` 和 `tcp_rejected_connections` 是运行期诊断，拒绝累计自启动以来计数并以 `u32` 饱和；可在 `/getsystemstatus` 用于发现连接槽压力。
- 本轮未测试 Modbus 写入/DO 动作、配置保存、AI/NFC、LoRa、RS485 主站外设轮询、链路断线恢复之外的物理故障注入，也没有执行 7×24 小时寿命试验。

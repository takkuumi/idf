# v2.6.0 F3 TCP 预算收紧复测（2026-11-03）

## 变更

- `MAX_REQUESTS_PER_TICK`: `2 -> 1`，每个 5ms main loop tick 只准入一个完整 Modbus TCP 业务请求。
- `MAX_TCP_WORK_US`: `2500 -> 1500`，新业务请求的准入窗口收紧；已有响应刷新、超时检查、连接轮转和协议编码不变。
- 单个不可分割的大请求仍可能超过窗口，因此该窗口不是硬中断机制。

这组参数优先保护 IO、BLE、AI 和看门狗的调度余量，代价是四端口峰值吞吐下降、请求排队延迟上升。

## 固件与测试

- 设备：ESP32-S3 F3，v2.6.0，重新完整刷入并逐段 hash 校验；业务 NVS 保留。
- 测试：四个持久 TCP 连接，端口 `502/503/504/5002` 各一条；120 秒；每 20ms 开始一轮；轮询 FC01、FC02、FC03（125/16 words）和 FC04（AI/状态/版本）。
- 主机逐请求校验事务号、MBAP、功能码、字节数和响应长度。

## 设备侧结果

当前串口窗口内无复位、无看门狗、无异常堆耗尽：heap 约 `2041..2045KB`，内部 heap 最低约 `51KB`，RCU 最大回收等待约 `15us`。main loop 指标为：

| uptime 窗口 | max_work | deadline_miss | p95/p99 桶 |
|---:|---:|---:|---:|
| 60s | 9567us | 224 | 5000/7500us |
| 120s | 32541us | 920 | 7500/7500us |
| 181s | 34996us | 691 | 7500/7500us |

旧预算（每 tick 2 个请求、2.5ms 窗口）的同类压测记录为 `deadline_miss=3062`、`4527`，因此本次窗口超期次数下降约 80%–93%；但由于调度窗口和测试时间点不同，这不是严格统计学 A/B 实验。请求 P95 约从 22ms 增至 40ms，属于预算收紧的直接代价。

## 结论

本次参数把 TCP 压力从“高吞吐、明显挤压 main loop”调整为“零协议错误、较低 main loop 超期、较高请求排队延迟”。当前结果没有拖垮设备，适合先作为生产候选参数；生产 PLC 应避免无限制满速轮询，建议按实际点表和周期继续验证。若要求更低的实时超期，下一步应把大 FC03/FC04 编码移出 main loop 或拆分快照工作，不能继续单纯降低预算。

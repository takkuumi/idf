# v3.3.0 F3 RS485-2：9600 波特率读取规模与吞吐实测

日期：2026-11-15（Asia/Shanghai）  
时间：2026-11-15T09:32:05+08:00 至 2026-11-15T09:35:28+08:00

## 结论

9600 下并不存在统一的 200ms 应答等待。小请求（1/2/4/8 个寄存器）的完整往返
平均约 25.6/27.9/32.1/40.4ms；读 100 个约 232.5ms，读 125 个约 284.4ms。
本轮 9 档规模 × 2 种请求间隔 × 100 次 = 1800 次正式读取，全部通过；54 次
预热另计，UART2 收发和服务计数各增加 1854，UART0/UART1 均未增加。

## 测试条件与计时定义

- F3 v3.3.0，build ID `5161ae8c8983`；
  FC04 `0x087E` 读取版本 330，FC03 `0x08A5` 读取型号 243。
- 设备 IP `192.168.51.226`，外接 USB-RS485 `/dev/cu.usbserial-14140`，
  接入物理 RS485-2 / UART2；9600 8N1，从站地址 1。
- FC03，零基地址 2300；每档读取 1/2/4/8/16/32/64/100/125 个 holding 寄存器。
- 每次按站号、功能码、byte count、完整长度、CRC 和 TCP 基准逐字节校验。
- **完整往返**：在 `serial.write` 前采样单调时钟，完整应答收齐后结束；包含请求
  发送、等待响应、响应接收以及 PC/USB/OS 调度。它不是示波器测得的 MCU 响应时间。
- **吞吐**：成功事务数 / 整档实际墙钟耗时；包含请求间隔、Python 和日志开销。
  有效寄存器/秒 = 成功事务数 × 本档寄存器数 / 耗时，不包含协议头和 CRC。
- 两种间隔：完整应答收齐后立即发下一笔（脚本不额外 sleep）；以及每笔应答后
  额外请求 sleep 4.2ms。后者受 OS 调度影响，实际停顿可能更大。0ms 是“无额外
  软件停顿”，不代表物理线路帧间静默为零，也不是要求现场 PLC 取消协议间隔。
- 每档 3 次预热单独记录，排除在延迟/吞吐统计外。
- 本轮只读取设备，未刷机、改波特率/组态或切换 IO。

## 为什么 100 个寄存器超过 200ms

按本次实际 8N1 配置，每个字节在线路上为 10bit（1 起始 + 8 数据 + 1 停止）：

- FC03 读 100 个的响应：`1 站号 + 1 功能码 + 1 byte count + 200 数据 + 2 CRC`
  = 205 字节；仅响应序列化 = `205 × 10 ÷ 9600` = **213.542ms**。
- 加上 8 字节请求，纯字节序列化 = `213 × 10 ÷ 9600` = **221.875ms**，
  尚未计帧间静默、软件处理和 USB/OS 延迟。
- 只读 1 个寄存器时，响应 7 字节，请求 8 字节，总共 15 字节的纯序列化为
  **15.625ms**。本次实测平均 25.620ms，多出的部分包含固件静默收帧、任务
  调度以及主机转换器开销，不能全部归因于固件。

因此少量读取提高的是更新次数；批量读取提高的是每秒有效数据量。这两种指标
不能混为一谈。上述只是当前接线、负载、PC 工具下的观测值，不是 7×24 最坏时延
保证。

## 历史计时口径修正

此前 `/tmp/imc_rs485_soak.py` 虽在 `write` 前保存了一个时间变量，但后续没有
使用，而是在 `read_rtu_frame()` 内重新开始计时。因此刷后 RS485-1 的
220.314ms，以及同脚本测得的 RS485-2 221.444ms，是发送/flush 完成后的接收
耗时，**不是从发起请求到完整应答的往返时间**。计数、CRC 和数据一致性结论仍
保留，但不能将该时间与本次完整往返直接比较。本次请求 write/flush 通常约
10–11ms，读 100 个的完整往返在 232ms 左右。

同时纠正端口角色表述：当前两路均配置为从站，走
`rtu_runtime::port_loop -> Rs485Port::read -> handle_request_stream`，端口号没有
把 RS485-1 永久固定为主站、RS485-2 固定为从站；角色由配置与 RS485-1 拨码覆盖
策略决定。

## 运行态复核

- 正式读取 1800/1800，预热 54/54，无超时、CRC 错或数据不一致。
- UART2：RX/TX/service 各 +1854，TX errors +0，driver opens +0。
- UART0/UART1：RX/TX/service 均 +0，确认此次请求实际进入 UART2。
- reset count：155 → 155；
  uptime 单调增加，没有本轮测试导致的复位。
- recovery mode 保持 Normal；recoverable 计数保持
  2，degradable/severe 保持 0。

## 实机发现与修复

### 组态最后一块提交触发 PANIC

- 旧镜像 B1 表头应答正常，最后 B3/FC16 数据块提交时连接断开。Web 查询复位计数从 108 增至 109，`reset_reason=4 (PANIC)`。
- 发布 ELF 反汇编：`main_loop=6480`、协议处理 `1328`、暂存提交入口 `14416`、提交/回滚 `6976` 字节，四个主要嵌套栈帧已合计 **29200 字节**；实际 SDK main 栈只有 **24576 字节**，尚未计其它调用帧。
- 去除大型定长表跨 `Option/Result` 的栈复制。暂存数据采用校验长度后一次 fallible reserve 的有界缓冲区；回滚保留 RCU 不可变快照，不再复制整张 1700-word 表。
- 没有增大 SDK 任务栈。修复镜像相同四个关键栈帧为 3120、1328、704、816 字节，合计 **5968 字节**。
- 栈预算常量由错误的 32 KiB 更正为实际 24 KiB，并通过 host 检查保持与 SDK 配置一致。
- 修复后已完成 22 次同内容组态提交（包含末块 ATT 写完立即断开）；直接读取 Flash，两个槽 CRC 正确，generation 从 68 推进到 90，组态/文本保持一致。
- 崩溃后 coredump 分区内容全 FF，本轮没有可用的崩溃回溯；栈占用证据来自实际发布 ELF，不能写成已解析 coredump。

### 并发负载中蓝牙完整请求偶发丢失

- 第一版栈修复后的混合压力测试捕获一次 8 秒请求超时，复位计数不变，BLE drop 计数增加 1；该轮未记为通过。
- 接收请求采用 `MpscRing::try_enqueue`，它在短暂队列锁竞争时也会返回失败；该路径已先发送 GATT 写成功，应答后丢弃完整帧会造成客户端超时。
- 改为 4 个既有接收槽的原子 pending 位及 FIFO ticket 调度。新请求发布不依赖消费者锁；重试保持原 ticket，保持分块组态顺序。
- 新增实际调度器 host 测试，覆盖 FIFO、重试、ticket 回卷、重复合并和 20000 次并发发布/消费；保持现有会话/断线请求权限检查。

## 最终修复候选的实机结果

- 镜像：F3/LoRa，app **1,842,992 字节**，SHA-256 `9b39ac4d6da5d854d4990f934c7099ede57b1b116d21635b2fc5fb88544b1cfe`；最终从设备 Flash 回读逐字节匹配。保留原 IP、网关、NVS、组态和文本配置。
- BLE：总计 **3154 次成功请求**。其中持续混合读压测 **180.45 秒、400 轮**，无请求超时、CRC/帧解析错误，fault/drop 五计数始终 `[0,0,0,0,0]`，复位计数保持 113。整轮还包含完整组态/文本快照、5 次断开重连、保存立即复位及 10 次组态提交；没有用客户端重试掩盖失败。
- BLE 混合读请求的 RTT（含主机/macOS/BLE 链路）平均 64.14 ms、P95 90.12 ms、P99 118.72 ms。配置写入包含 ATT 分片与同步落盘，不与普通读 RTT 混算；完整轮次最大请求时延为 659.25 ms。
- 5 次 BLE 重连并读取身份/版本均成功，用时约 1.01–1.13 秒。最后断开后重新扫描可发现广播。

### 失败记录的处理

- `ble-main` / `ble-main-corrected` 为测试端 AT 外层帧、变长 location 别名适配过程，不当作固件性能结论。
- `ble-logic-upload` 保留原版 PANIC 现场；`fixed-full-acceptance` 保留第一次栈修复后捕获的 1 次 BLE 超时/drop，未记为通过。
- 中间 90 秒网络轮次与上述失败后的计划复位重叠，不能作为干净并发通过证据。最终依据 `final-fixed-network-ble-120s.jsonl` 和 `final-fixed-ble/`。

## 硬件边界

- 本轮没有切换 Q 点；当前 Q6/Q7 的 PCA9555 输出寄存器读回为 `0x0060`，不等于测量了继电器触点或外接负载响应。
- 实际 RS485 收发器、LoRa 射频对端、NFC RF/手机及 AI 标准电流源未完成本轮物理闭环。USB/UART0 探测未获得有效 RTU 应答，不能替代两路物理 RS485 验收。
- 短时实机压力结果不等价于 7×24 或可用性“几个 9”的证明。

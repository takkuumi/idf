# LoRa 硬件分析与验收边界

## 结论

当前 Rust 固件没有 LoRa 射频驱动，也没有 SX127x、SX126x、LLCC68、LoRaWAN 或其它 LoRa 芯片的 SPI/UART 初始化、复位引脚、IRQ 引脚和寄存器识别代码。因此当前版本不能宣称 LoRa 功能可用，也不能仅靠 Web 或 BLE 状态页证明板上存在 LoRa 芯片。

## 旧固件得到的证据

旧工程 `MCA_F16V2_1_F48_BLE` 的 `utilities.h` 只定义了 ESP32-S3 板载 W5500 和 SD 的引脚，没有 LoRa 芯片的 SPI 片选、复位、DIO/IRQ 或射频频段配置。

旧工程把第三路串口称作 `RoLa`，但实现是：

- `Serial` / UART0，默认控制台引脚 TX=GPIO43、RX=GPIO44；
- 启动时读取第三路 RS485 配置；源码注释 `Lora reset` 只出现在读取 Slave ID 的旁边；
- 从站模式读取 UART0 字节并交给 Modbus RTU 解析；主站模式通过同一个 UART0 发送 Modbus 请求。

旧工程没有 LoRa 芯片型号、无线寄存器读写、频率/扩频因子/带宽/功率配置或 LoRaWAN 入网流程。由源码证据看，“LoRa”更像接在第三路 UART/RS485 上的外部透明无线 Modbus 模块，不能反推出具体射频芯片型号。

## 当前设备能安全探测什么

可以安全确认：

1. 主控启动日志和 GPIO/UART 配置是否包含第三路 UART0。
2. 设备是否在 GPIO43/44 接收到外部串口活动（需要示波器或逻辑分析仪，不能仅凭软件空闲读取区分“无模块”和“模块无数据”）。
3. 如果确认外部模块协议，再通过其只读 AT/状态命令读取型号和固件版本。

不能安全推断：

- 仅凭串口没有响应就判断“没有 LoRa”；
- 在未知协议下盲发命令；
- 把 Modbus `mode=3` 当作 LoRa 驱动状态。

## 现场确认步骤

1. 断电查看板卡 BOM、丝印和模块照片，确认是否存在独立 LoRa 模块及型号。
2. 查模块数据手册，确认它接的是 UART、RS485 还是 SPI，并记录供电、波特率、默认地址、复位和 IRQ。
3. 若为 UART/RS485 透明模块，使用隔离 USB-UART/RS485 转换器在 GPIO43/44 对应接口做只读监听；先确认空闲电平、波特率和帧格式，再发送数据手册规定的查询命令。
4. 若为 SPI LoRa 芯片，必须确认 CS、RESET、DIO1/DIO0、BUSY 和电源控制引脚后，才能编写不会影响 W5500 的独立探测驱动。
5. 只有完成型号识别、回环/点对点收发、断电重启和连续运行测试后，才能把 LoRa 标为生产功能。

## 当前产品决策

在硬件型号和接口协议确认前，第三路 `mode=3` 保留并按安全的非 LoRa 路径处理；产品文档不宣称 LoRa 已支持。这样不会把未知串口数据误当成无线链路，也不会向未知硬件发送可能改变配置的命令。

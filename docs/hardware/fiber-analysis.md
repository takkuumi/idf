# 双光纤功能调查与验收边界

调查日期：2026-10-30。对象：当前连接的 ESP32-S3 板卡，固件 v2.2.8，IP `192.168.51.226`。

## 当前结论

尚不能把两路光纤标为“已正常运行、已验收”。新旧固件均通过一个 W5500 接入以太网，
没有找到旧固件中存在而新固件遗漏的独立双光口初始化逻辑。但当前能访问 Web/Modbus，
只能证明电脑到设备的现有路径可用，不能证明该路径经过光口，更不能证明两个光口各自
收发、光口间转发或环网故障切换正常。

如果板卡支持双光口转发，它可能由外部交换/光电转换硬件完成；这是根据 MCU 接口做出的
推断。项目中未找到该板光口芯片的型号、原理图、端口连接关系和环网协议资料，不能据此
确定硬件拓扑、交换能力、速率或冗余收敛时间。单个 MCU 网络接口本身也不能作为“不支持
双光口转发”的证据。

## 源码核对

| 项目 | 实际实现 | 能证明什么 |
| --- | --- | --- |
| 当前 MCU 网络 | `src/ethernet/w5500.rs::start` 创建一组 W5500 MAC/PHY 和一个 netif；SPI 40MHz | 应用使用一个 W5500 网络接口 |
| 旧固件网络 | `utilities.h` 实际选择 ESP32-S3；主程序调用 `ETH.beginSPI`，`ETHClass.cpp` 创建 W5500 MAC/PHY | 旧固件该构建分支也不是双独立 MCU 以太网接口 |
| 两路检测输入 | `src/hal/mod.rs::fiber_status` 读取 GPIO39/40，低有效；旧程序直接读取同样引脚并取反 | 两个硬件输入的电平语义一致；具体硬件信号含义仍需板级资料确认 |
| 光纤实体灯 | 主循环每 100ms 复用输入更新 PCA9555；Web 复用同一个函数 | 软件检测值与灯输出目标一致；灯亮不等于数据收发成功 |
| 链路速率日志 | `log_link_transition` 查询 W5500 PHY | 不是两个光口各自的协商速率或光功率 |
| 以太网心跳 | `heartbeat_once` 检查本地 PHY 链路及非零 IP | 不检测远端可达性，也不检测环网收敛 |
| UDP 交换机状态 | `src/udp_multicast/mod.rs` 接收并过滤来源，向 FC04 `0x0090` 状态区提供数据 | 仅状态接收；不是光口转发、交换芯片初始化或环网控制 |

在所检查的新旧源码中没有找到当前 ESP32-S3 构建分支用于双光口的交换芯片管理初始化，
也没有找到 STP/RSTP/ERPS/MRP 等环网控制实现。不能把通用 `ETHClass` 中其它板型的
RMII/MDIO 分支当作本板实际使用的驱动。

旧 `src/ethernet/mod.rs` 注释曾写“20MHz、ping 对端、超时复位、简单冗余”，与实际代码
不符。本轮仅纠正该模块说明，未修改网络运行逻辑、设备配置或重新刷机。

## 本轮实机证据

2026-10-30 11:41:07（Asia/Shanghai）读取：

- `ethernet_link=true`，设备 uptime=611 秒，reset_count=46，Recovery=Normal，故障计数全零。
- `state_addr_6=0`、`state_addr_7=0`，即 FIB1/FIB2 两个检测输入均未激活。
  此结果不能区分未接光纤、对端未就绪、硬件检测接线变化或其它硬件原因。
- UDP 接收字节数为 0，FC04 `0x0090` 起 16 words 全零。当前有效组播配置为
  `239.0.0.1:5003`，源过滤 `192.168.51.201`；该源地址来自保存配置，并未证明它就是板上
  光纤交换硬件。没有收到状态包不能直接判定光口故障。
- 30 秒串口采集 `sessions=1 / reopen_errors=0`；采集窗口没有观察到 panic、看门狗复位
  或以太网链路切换。它不覆盖设备的完整运行历史。
- 当前网络路径的 30.4 秒四端口 Modbus 轮询：240 轮，239 成功、1 次异常响应 `0x02`
  （端口 504）。原测试每轮顺序读四段，未记录失败的具体地址，因此本次结果不能写成
  “全通过”，也不能把协议层的合法异常响应直接归因于光纤丢包。
- 随后 11:43:00 至 11:44:01 进行逐请求记录的四端口复测，顺序读取 FC04 `0x0080/8`、
  FC04 `0x0088/8`、FC03 `2280/16`、FC04 `0x087E/2`，共 3,984 次请求、0 错误。
  初次异常未复现，根因未确定，不能据此认定已修复。静态检查发现 `encode_hold_regs_be`
  和 `encode_input_regs_be` 会对所有读取检查全局模拟量/RS485 结果版本，并在四次尝试
  均冲突后返回 `false`；协议层会统一映射为 `0x02`。这是需要进一步定点验证的候选原因，
  尚未取得该异常确实由版本冲突触发的设备证据。本轮没有改动该数据一致性机制。
